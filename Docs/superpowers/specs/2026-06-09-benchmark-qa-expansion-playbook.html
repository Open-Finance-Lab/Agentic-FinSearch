00Read this first

You generated 300 questions straight from SEC filings, each carrying its own answer and the exact facts that answer was built from. That is real work, and it already passes a solid set of automatic checks. This playbook is about the next job your professor asked for: turning those one-time checks into a standing quality process, so the set can be trusted and can keep growing without breaking.

◆ The one idea behind everything here

“Continuous QA” is not “check the file once.” It is a checklist you can re-run on command, every time the set changes. The set is only ever allowed to grow while that checklist stays green. A growing benchmark with no standing checklist quietly rots; this playbook is the checklist.

This document is deliberately written so you can act on it without further instructions. Every check below tells you what it looks at, and exactly what counts as passing. It does not tell you which tools or code to use — that comes later, in a separate implementation spec built from this doc. Your job in this phase is to make each check real and repeatable, however you choose to build it.

What is already verified (your structural QA — done)

✓ Passing today, before any further work
  • Every fact a question points to exists — no answer cites evidence that can’t be found.
  • No two questions use the exact same evidence set, and the answer value never appears inside the question text.
  • No future data — every fact was filed on or before the question’s cutoff date.
  • The math was re-derived — 204 computational answers were recomputed from their inputs with zero mismatches, and 51 “first year a condition holds” questions were re-checked with zero failures.
⚠ What is not done yet (this is the gap)

Nobody has read a sample by hand to judge whether the questions are clear and whether each gold answer is the only defensible one. The checks were run once, not wired to re-run. The set is lopsided (one template is a third of all cases). And the old cases (2011-era) raise a memorization question. Sections 03–06 close each of these.

03Build the standing QA checklist

Turn the one-time checks into a checklist you can run on the whole set in one go, which prints a short pass/fail report. Below are the ten checks it must contain. The first five you have already done once — now they become permanent. The next two are new correctness checks borrowed from prior benchmarks. The last three are quality reports that flag things for human judgment rather than pass/fail outright.

Group A — Integrity (must be green)

C1 · Evidence exists

Every fact a question relies on can be found in the fact store.

Pass: zero questions whose evidence is missing or unresolvable.
On fail: quarantine the case; it cannot ship until its evidence resolves.
C2 · No duplicate evidence sets

No two questions are built from the identical set of facts.

Pass: zero exact collisions. (Near-identical wording is a separate check — C8.)
On fail: drop one of the pair, or change one so it asks something genuinely different.
C3 · No answer leakage

The answer value never appears in the question text.

Pass: zero questions that hand the answer away.
On fail: rephrase the question so the value must be looked up, not read off.
C4 · No future data (the as-of rule)

Every fact used was filed on or before the question’s cutoff date.

Pass: zero facts filed after the cutoff.
On fail: either move the cutoff forward, or drop the offending fact.
C5 · The math re-derives

For every computed answer, recomputing it from the cited inputs gives the same number.

Pass: zero mismatches (allowing the small rounding tolerance the Owner’s Guide sets).
On fail: the case is wrong — fix the inputs or the formula, do not ship it.

Group B — Correctness, new checks FINAUDITING

C6 · Subtotals reconcile

Wherever an answer uses a subtotal (total revenue, total assets, equity…), that subtotal equals the sum of its parts as the filing itself defines them — signs included.

Filings carry their own “these line items add up to that subtotal” relationships. Re-add the parts and confirm they match the reported subtotal. If a number is disconnected from its parts, the fact itself is suspect — not just the question.

Pass: every aggregate used reconciles to its components within tolerance.
On fail: flag the underlying fact; do not build questions on a number that doesn’t add up.
C7 · Accounting identities hold

Where it applies, confirm Assets = Liabilities + Equity for the company and period the question uses.

Pass: the identity holds within tolerance for every case that touches the balance sheet.
On fail: the period’s figures are internally inconsistent — investigate before using them.

Group C — Quality reports (flag for human review, don’t auto-fail)

C8 · Near-duplicate wording QuantEval

Flag pairs of questions that are near-identical in shape and wording, so the set isn’t padded with cosmetic variants.

This matters most for the largest template (see C9): 102 of the 300 questions follow the same “how did metric X change from year A to year B” shape, so many will read almost the same. QuantEval’s rule of thumb: when two items score above 0.92 similarity, review them as a likely duplicate.

Outcome: a list of suspected duplicate pairs for a human to keep, merge, or cut.
C9 · Distribution report

Count cases per template, track, difficulty, and era; flag any template above 25% of the set.

Outcome: the table in section 05, refreshed on every run, so imbalance is visible.
C10 · Era report

Count cases by how old the cutoff date is (e.g. before vs after 2020), and report the old-case share.

Outcome: a number the Owner uses to apply the era policy (section 05).
What “the checklist is green” means
  • Checks C1–C7 all pass with zero failures.
  • Checks C8–C10 have been produced, and every flag they raised has been reviewed and resolved.
  • The run produces a one-page report (date, set version, every check’s result and counts).

04The human spot-check

Machines confirm the facts; only a person can confirm the questions read well and have a single defensible answer. This is a small, structured read — not a review of all 300.

Step 1 — Pick the sample

Read about 30 cases (or 10% of any new batch, whichever is larger), chosen to cover the variety, not at random across the whole pile:

  • At least a few from every template, roughly in proportion to its size.
  • At least one from each difficulty level (easy, medium, hard, very hard).
  • At least two old cases (pre-2020 cutoff) and two recent ones.
  • No more than two or three from the same company, so the sample isn’t dominated by one filer.

This “cover the variety on a small budget” sampling mirrors how FinTagging chose its audit set FinTagging.

Step 2 — Score each case against five questions

R1 · Readable — Is the question grammatical and unambiguous about the company, the metric, and the period?
Watch for: vague periods (“recently”), missing units, or a company named in a way that could match two entities.
R2 · Single defensible answer — Given the filing, is the gold answer the only reasonable answer?
Watch for: a metric that the company reports two ways (e.g. revenue under different labels), or an equity figure that may or may not include non-controlling interest — either can make a second answer arguable. If so, the question must pin down which one it means.
R3 · Faithful evidence — Do the cited facts actually support the answer, and are they from the right filing and period?
Watch for: the right number from the wrong year, or a comparative column mistaken for the primary figure.
R4 · No shortcut — Is the question impossible to answer from its own text or general knowledge alone — does it truly require the data?
Watch for: famous round numbers, or old cases whose answers a model might simply remember.
R5 · Difficulty feels right — Does the assigned difficulty match the actual effort, or is a “hard” case trivial (or vice versa)?
Note: difficulty today is set purely from how many facts are needed. R5 is the human sanity check on that proxy.

Step 3 — Two readers, one judge

To keep this honest, not a rubber stamp:

  1. Calibrate first. Both reviewers score the same 5 cases together and talk through any disagreement, so “pass” means the same thing to both.
  2. Review independently. Each reviewer then scores the rest of the sample on their own, marking each of R1–R5 pass or fail with a one-line note.
  3. Adjudicate. A senior person (Felix or the advisor) resolves every disagreement, producing the final verdict per case.
◆ How we know two readers agree

Report a simple agreement score — how often the two reviewers reached the same verdict, corrected for the agreement you’d expect by chance (this is “Cohen’s kappa”; a person needs no formula, just the number). FinTagging reached 96% raw agreement, kappa 0.81 on the same kind of task FinTagging. The Owner’s Guide sets kappa ≥ 0.8 as the bar. If you’re far below that, your rubric isn’t being read the same way — recalibrate and re-review, don’t just push the cases through.

The point of QA is to let the set grow. Growth should move the set toward balance, not away. Here is the current shape and where it needs to go.

Difficulty and era

  • Difficulty spread is currently 10% easy / 45% medium / 30% hard / 15% very hard — a reasonable shape. Keep roughly this balance; let the human spot-check (R5) catch cases whose label doesn’t match reality.
  • Era policy (decision for the Owner to ratify): cutoff dates run back to 2011. Old, well-known figures risk being answered from memory rather than from retrieval, which is exactly what this benchmark is meant to measure. Recommended default: flag every pre-2020 case and cap them at a modest share of the set (the Owner sets the exact number). New cases should lean recent.

06The expansion workflow

Every time you add cases, follow the same loop. This is the “continuous” in continuous QA.

  1. Generate the new batch, aiming at the under-filled templates from section 05.
  2. Run the full checklist (section 03) on the whole set. It must come back green — integrity and correctness with zero failures, quality flags reviewed.
  3. Check the distribution moved the right way. The new batch should bring the set closer to the targets, never further from them.
  4. Spot-check the new batch (section 04) with the same rubric and the two-reader process.
  5. Version and document. Bump the version (v1 → v1.1), and add one changelog line: what was added, how many, and which templates.
  6. Hand it to the Owner’s gate (companion doc) for blessing.
⚠ The one rule that protects everything

Never add to an already-released version in place, and never expand while the checklist is red. Every change produces a new version with its own report. That is what lets anyone trust a set that keeps growing.

07Definition of done — what you hand over

A batch is ready for the Owner’s blessing when all of the following are true. This is the handoff contract between you and Felix.

A case (or batch) is done when…
  • It passes integrity checks C1–C5 and correctness checks C6–C7 with zero failures.
  • Quality flags from C8–C10 have been reviewed and resolved (duplicates cut, no template over 25%, era policy applied).
  • It was covered by a human spot-check that met the agreement bar (kappa ≥ 0.8) and passed the rubric — with zero R2 “ambiguous answer” failures in the sample.
  • It is recorded in the dataset card and changelog with its template, track, difficulty, and era.

08Grounded in prior work

◆ Where these methods come from

FINAUDITING — a sibling XBRL benchmark from our own lab circle. We borrow its idea of checking that subtotals reconcile to their parts and that accounting identities hold (checks C6–C7), and its practice of double-checking a large share of cases by hand.

FinTagging — an XBRL tagging benchmark. We borrow its human-review protocol: cover-the-variety sampling, two independent reviewers plus an adjudicator, a calibration round, and reporting an agreement score (section 04).

QuantEval — a quantitative-finance benchmark. We borrow its near-duplicate screen (flag items above 0.92 similarity, check C8) so the set isn’t padded with cosmetic variants.
