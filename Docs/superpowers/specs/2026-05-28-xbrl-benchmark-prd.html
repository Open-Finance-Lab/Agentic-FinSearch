TL;DR — What We're Building

We're building a benchmark that measures how well AI agents retrieve and compute financial facts from SEC filings. Unlike existing benchmarks that rely on human-curated answer keys or LLM-as-judge, ours generates questions directly from authoritative XBRL data — so every gold answer and gold solution-path exists by construction, no manual labeling needed.

◆ Core Thesis

Questions generated from grounded XBRL facts carry their gold answer and gold fact-path automatically. This means verifiability is the generative principle of the benchmark, not a bolt-on — no human answer-keys, no LLM-as-judge ambiguity.

⚠ The Gap

The current system validates against 3 local filings (AAPL FY2023, MSFT FY2023, TSLA FY2023) with 3 ratios. That's enough for a demo, but cannot generate or grade a benchmark across companies and periods. Closing this gap is the entire point of this PRD.

The Two Benchmark Tracks

Track R — Multi-Hop Retrieval (长程取数)

Measures how well an agent fetches K grounded facts across multiple hops: conditional lookups, period-over-period comparisons, cross-entity queries, multi-constraint filters.

◆ Example Question

"By how much did Apple's effective tax rate change between the first fiscal year its R&D exceeded $25B and the following year?"

Solution path: find-the-year → rate(y) → rate(y+1) → Δ  —  4 hops, each independently verifiable.

Metrics (mirroring 同花顺 evaluation framework):

MetricMeasures
End-to-end task accuracyFinal answer correct?
Per-hop process accuracyOf N hops, how many intermediate facts were correct?
Hop efficiencyFewer hops to solve = better. Penalizes unnecessary tool calls.

Track C — Complex Computation (复杂金融计算)

The agent plans and writes computation logic to derive a quantity from grounded facts — no pre-built tool for every metric. Tests on-the-fly reasoning, not memorized formulas.

◆ Example Question

"Calculate Microsoft's DuPont decomposition (net margin × asset turnover × equity multiplier) for FY2023 and identify which component changed most vs FY2022."

Requires fetching 6+ facts across 2 periods, applying 3 formulas, and a comparative judgment.

Metrics:

MetricMeasures
Result correctnessWithin decimals-aware tolerance of the deterministic gold answer
ExecutabilityDoes the agent's computation actually run without errors?
Internal consistencyDo intermediate values satisfy axiom constraints (e.g., A=L+E)?

The Verifiability Model

Four kinds of verifiability, each generalizing something we already ship:

#TypeHow It WorksGeneralizes
1 Provenance Every fact → a specific XBRL context (accession, tag, period, unit, context) tagging + query_xbrl_filing
2 Value Claimed value == authoritative XBRL value within decimals-aware tolerance Numbers & Ratios L1
3 Path Each hop's intermediate fact is independently checkable → process accuracy, not just final to build
4 Computation Derived result re-computable from grounded inputs + axiom consistency Axiom Engine

Data Layer: The Canonical Truth Store

◆ Key Decision: Context-Keyed Facts, Not Tag→Value

A US-GAAP tag is not a unique key. In one Apple 10-K, RevenueFromContractWithCustomerExcludingAssessedTax appears ~15+ times — FY2023/2022/2021 comparatives, plus product-line and geographic disaggregations. The key is the full XBRL context tuple.

Fact Table Schema (DuckDB)

CREATE TABLE facts (
  fact_id       VARCHAR,    -- hash(context tuple + accession)
  cik           INTEGER,
  entity_name   VARCHAR,
  taxonomy      VARCHAR,    -- 'us-gaap' | 'dei' | 'ifrs' | extension
  concept       VARCHAR,    -- the XBRL tag
  period_type   VARCHAR,    -- 'instant' | 'duration'
  period_start  DATE,
  period_end    DATE,
  unit          VARCHAR,    -- 'USD' | 'shares' | 'pure' | 'USD/shares'
  decimals      INTEGER,    -- precision → tolerance during matching
  dim_hash      VARCHAR,    -- dimensional members; NULL = aggregate
  segment_json  JSON,
  value         DOUBLE,

  -- provenance (verifiability + leakage control)
  accession         VARCHAR,
  form_type         VARCHAR,
  filed_date        DATE,
  fy                INTEGER,
  fp                VARCHAR,
  taxonomy_version  VARCHAR,
  frame             VARCHAR
);

CREATE TABLE filings (
  accession        VARCHAR PRIMARY KEY,
  cik              INTEGER,
  form_type        VARCHAR,
  filed_date       DATE,
  period_of_report DATE,
  primary_doc_url  VARCHAR,
  taxonomy_version VARCHAR
);

-- Key indexes
CREATE INDEX idx_entity_hist ON facts(cik, concept, period_end);
CREATE INDEX idx_cross_entity ON facts(concept, period_end);
CREATE INDEX idx_leakage ON facts(filed_date);

◆ Key Decision: Never Overwrite on Restatement

A 10-K/A can report a different value for the same (cik, concept, period). Store all facts from all filings. Resolve "the" value with an as-of query: WHERE filed_date <= D, take latest-filed — this automates leakage control. Restatement detection itself becomes a benchmark question type.

Concept Normalization

Companies tag the same economic concept differently (Revenues vs RevenueFromContractWithCustomerExcludingAssessedTax vs extensions). FinTagging measured: fine-grained concept linking peaks below 19% accuracy, and ~0% F1 when posed as single-step full-taxonomy tagging.

Solution: generalize the shipped RATIO_TAG_MAP into a config-driven canonical metric → ordered list of acceptable tags map, with explicit NOT_APPLICABLE handling (e.g., banks lack AssetsCurrent).

Validity Controls

  • Difficulty control: parameterize K (hop count) and formula complexity; target distribution across easy/medium/hard
  • De-duplication: no two questions should test the same fact-path with cosmetic rewording
  • Leakage scan: verify no gold answer is derivable from the question text alone
  • Human spot-check gate: sample ~30 cases for manual review before the pilot is "blessed"
  • Distractors: plausible-but-unambiguously-wrong; questions require reasoning, not keyword matching

Grading Harness

Track R Grading

Capture the agent's structured tool-call trace. Align it to the gold fact-path. Grade on facts reached (set/DAG equivalence), not literal tool-call order — a question may have multiple valid solution paths.

◆ Key Decision: Set/DAG Equivalence, Not Exact Sequence

The gold path is a sufficient path, not the only path. Two agents that reach the same correct intermediate facts via different tool-call orderings should both score full marks on process accuracy.

Track C Grading

  • Value correctness: ValidateMetric re-computes from grounded inputs within decimals-aware tolerance
  • Executability: does the agent's computation run without errors?
  • Axiom consistency: intermediate values satisfy known constraints (A=L+E, etc.)

Load-Bearing Design Decisions

These are the decisions that shape the whole system. Changing one shifts the design.

ADR-01 — Context-keyed fact table, NOT tag→value

Why: One US-GAAP tag maps to many facts in a single filing (comparative years + segment/geographic dimensions). A tag→value map silently collapses the exact ambiguity verification exists to resolve.

Consequence: The key is (cik, concept, period_type, period_start, period_end, unit, dimensions). Value carries decimals + provenance.

ADR-02 — Flat facts are truth; filing tree is a view

Why: A fact lives at the intersection of (entity × concept × period × dimensions) — 4-dimensional. A single tree forces one hierarchy and loses the rest.

Consequence: Store flat facts. Expose period-tree and per-filing statement-tree as materialized views for navigation.

ADR-03 — Store every filing's facts; never overwrite

Why: A 10-K/A can report different values for the same tuple. Overwriting destroys both as-of/leakage-control and restatement detection.

Consequence: filed_date is part of the key. "The" value is an as-of query. Restatements become benchmark question types.

ADR-04 — Breadth-first companyfacts; iXBRL is a depth tool

Why: companyfacts gives a company's full pre-parsed history with provenance in one call. Dimensional depth is a minority need for the benchmark.

Consequence: Fast path to benchmark scale. The existing iXBRL parser is reserved for segment-level facts (deferred).

ADR-05 — Local-first (DuckDB) → cloud-later

Why: Prove the benchmark's value before paying cloud complexity. DuckDB handles millions of facts with zero infra.

Consequence: Phase 5 cloud migration is a clean hand-off to the lab's grant track, not a prerequisite.

ADR-08 — No LLM in the validation or grading path

Why: A verifier that hallucinates is worthless. The moat is deterministic checking against the primary source.

Consequence: ValidateMetric, axiom checks, and grading are pure code with decimals-aware tolerance. LLMs only generate questions (in the template engine), never adjudicate (no LLM-as-judge).

ADR-11 — Grade on facts reached (set/DAG equivalence)

Why: A multi-hop question can have multiple valid solution paths. Exact-sequence grading punishes correct alternatives.

Consequence: The gold path is a sufficient path. Process accuracy measures intermediate facts reached, not tool-call order.

Getting Started — Week 1 Checklist

Concrete first steps to get the fact store populated and validate the approach:

  1. Set up the project structure. Create a benchmark/ directory in Main/backend/ with: ingest/, store/, templates/, grading/.
  2. Get the S&P 500 CIK list. SEC publishes this. Map ticker → CIK for the universe.
  3. Write the companyfacts ingestion script. For each CIK: fetch data.sec.gov/api/xbrl/companyfacts/CIK{cik:010d}.json, parse the JSON structure, insert into the DuckDB facts table. Respect User-Agent header and ~10 req/s throttle.
  4. Regression test. Run the existing axioms/benchmark.py 3-case benchmark but resolve values from the new DuckDB store instead of local iXBRL files. All 3 must still pass.
  5. Stats check. Print: total facts, unique companies, temporal range, top-10 most-reported tags.

SEC API Quick Reference

⚠ SEC Fair Access Rules

All requests must include a User-Agent header with your name and email (e.g., FinSearch Lab felixflyingt@gmail.com). Max ~10 requests/second. Prefer bulk companyfacts.zip for the initial backfill. 

# All facts for a company (primary ingest path)
GET https://data.sec.gov/api/xbrl/companyfacts/CIK0000320193.json
#                                              ^^^^^^^^^^  (AAPL CIK, zero-padded to 10 digits)

# One concept across all companies in a period (cross-entity)
GET https://data.sec.gov/api/xbrl/frames/us-gaap/Revenues/USD/CY2023Q4I.json

# One concept's full history for one company (runtime hot path)
GET https://data.sec.gov/api/xbrl/companyconcept/CIK0000320193/us-gaap/Revenues.json

# Bulk download — entire corpus, no rate limits
GET https://www.sec.gov/Archives/edgar/daily-index/xbrl/companyfacts.zip

The companyfacts JSON structure nests facts under facts.{taxonomy}.{concept}[].units.{unit}[], where each entry has val, accn, fy, fp, form, filed, frame, start, end.

Open Questions for Discussion

  1. Concept-normalization scope: How many canonical metrics do we need before the 300-case pilot is "rich enough"? Starting candidates: revenue, net income, total assets, total liabilities, equity, current assets, current liabilities, COGS, R&D, operating income, cash & equivalents, total debt.
  2. K-distribution: What's the right mix of hop counts? Proposed: ~30% K=1 (baseline), ~40% K=2 (the "cliff"), ~20% K=3, ~10% K≥4.
  3. Track C scope: Start with valuation/metric-derivation only, or include strategy-coding with backtest execution in the pilot?
  4. Fiscal year normalization: SEC frames use calendar-year periods (CY), but companies have different fiscal year-ends. Rule for cross-entity comparisons?
