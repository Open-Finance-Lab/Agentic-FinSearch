00What this guide is for

Your teammate owns the hands-on QA and the growth of the question set (their playbook is the companion doc). You own three things they can’t: the bar — what “good enough to ship” means; the sign-off — declaring a version blessed; and the grading track — the machinery that turns the set into actual scores for an AI agent. This guide is written for someone running a benchmark for the first time, so it explains the why as much as the what, and it stays out of tools and code on purpose.

⚠ Out of scope here, by design

This is not an implementation spec. It tells you what the grader must measure and what a version must clear — not which database, library, or code to use. Those decisions belong in a focused build spec written from this guide, once the set is blessed.

01What “running a benchmark” actually is

The mental shift, if this is new: a benchmark is a released product with versions, not a file you make once. It moves through a repeating lifecycle, and your teammate’s QA is the loop that keeps it honest:

Construct→ QA-harden→ Freeze & version→ Grade agents→ Expand↶ (back through QA)

The set is built (done — v0). It now gets hardened and frozen into a trustworthy v1. Only then do you grade agents against it. When you grow it, the new cases loop back through the same QA before the next version. You are at the QA-harden step.

◆ The one sentence for your professor

“Continuous QA means we built a checklist we can re-run on the whole set on command, and the set is only ever allowed to grow while that checklist stays green. Each blessed version ships with its own report and changelog.” That single discipline is what makes a benchmark expandable instead of fragile — it is exactly the concern your professor raised.

02The acceptance gate — what makes a version “blessed”

This is the most important thing you own. The gate is the bar a set must clear to become a blessed, citable version (the first one being v1). You don’t re-run the checks yourself — you confirm they were run, read the evidence, and sign off. Tick every box before blessing:

v1 acceptance gate
  • Integrity is green — evidence exists, no future-data leakage, the math re-derives (checklist C1–C5 in the playbook, zero failures).
  • Correctness is green — subtotals reconcile to their parts and accounting identities hold (C6–C7, zero failures).
  • Quality flags resolved — near-duplicates removed, no single template above 25% of the set, era policy applied (C8–C10).
  • Human spot-check passed — the two-reviewer read met the agreement bar (kappa ≥ 0.8) and cleared the rubric, with zero “ambiguous answer” cases in the sample.
  • It’s documented — a dataset card and version tag exist, with counts and a changelog.

If any box is empty, the set is not v1 — it goes back to your teammate with the specific gap named. A gate that bends is not a gate.

03How to review your teammate’s QA

You don’t need to read the tooling. You need to read five pieces of evidence and do one small check of your own:

Look atYou’re confirming
The QA reportEvery integrity and correctness check came back green, on the current version, dated.
The spot-check logThe agreement score met the bar, and there are no unresolved “ambiguous answer” cases.
The distribution tableNo template exceeds 25%; difficulty and era look reasonable.
The changelog / dataset cardWhat changed since the last version is written down, with counts.
Five cases, read cold (your own check)Pick five yourself and try to find a second defensible answer to each. If you can’t, that’s a good sign; if you can, send it back.

Sign-off = tagging that version as blessed. From that moment it’s frozen: future changes create a new version, never an edit in place.

04The grading track — what the grader will measure

Once v1 is blessed, you build the grader: the machinery that runs an AI agent against the questions and scores it. This section is the specification of what to measure — the build itself is a later spec. A grader asks two things of any answer: did the agent get the right answer, and did it get there honestly — using the real facts, not a lucky guess?

TRACK R · retrieval questions

Score on which of the needed facts the agent actually reached.

Each question has a known set of facts its answer depends on. Measure two things: did the agent reach all of them (the all-or-nothing view), and what fraction did it reach (the partial-credit view). Crucially, don’t require the same route — a question can often be solved more than one way, so credit the facts reached, not the order or the exact path taken. FINAUDITING

TRACK C · computation questions

Recompute from the agent’s inputs, and report three things separately.

Don’t collapse computation into one right/wrong bit. Report, as three separate results: (1) did the agent produce a well-formed answer at all; (2) did it pull the right numbers; (3) did it do the math correctly. Keeping these apart means a formatting slip is never mistaken for a reasoning failure — you can see exactly where it broke. FINAUDITING

Tolerance: exact match for numbers copied straight from a filing and for identities that must hold precisely; a small, stated wiggle only where you divide (ratios, returns). This finally settles the “tolerance decided later” note left open in the set’s own documentation.

TRACK C · strategy-coding (later stretch)

Two separate scores: does it run, and how close is it?

If you later add questions where the agent writes a small strategy, score whether the code actually runs under fixed, no-peeking-at-the-future rules, and how close its results are to the reference — as two separate numbers. A run that doesn’t execute is “undefined,” not zero: you can’t be accurate if you didn’t run. QuantEval

◆ The headline result: the baseline comparison

Run the same agent twice — once with our truth layer, once without — and show the difference. This both quantifies the lift our work provides and reproduces, on our own data, the well-known finding that agent accuracy falls off a cliff once a question needs more than one step. That contrast is the single most compelling number to put in front of your professor and, later, a paper.

05The auditing tier — a QA gate now, a question family later

The subtotal-reconciliation and identity checks (C6–C7) do double duty. Today they are a quality gate: no question ships on a number that doesn’t add up. Later, the same idea becomes a new family of computation questions — “verify this subtotal,” “does Assets = Liabilities + Equity hold for this filing?” — that are fully checkable with no AI judge at all.

◆ Why this is a strategic win, not just a check

This kind of consistency-checking is the core of FINAUDITING, a sibling XBRL benchmark from our own lab circle. Adopting it aligns us with allied work, gives our benchmark harder, fully-deterministic headroom, and lets us frame our set as the complement of theirs: they detect filings’ errors, we generate verified questions from clean facts. Worth a sentence to your professor.

06Roadmap & what to report at each step

Four milestones, in order, each with a concrete thing to show your professor. No dates here on purpose — the sequence is the commitment; you set the pace.

M0 · Done

v0 pilot built, structural QA passing

300 cases generated from real filings; the machine-checkable QA already passes.

M1 · Now — this phase

Standing QA checklist + first human spot-check → v1 blessed

Your teammate makes the checklist re-runnable and does the first structured human read; you sign the acceptance gate.

Report to professor: “The set is now a versioned, re-checkable product — here is the QA report, the reviewer agreement score, and the blessed v1 of 300.”
M2 · Next

Grading harness → first agent evaluation

You build the grader (section 04) and run our agent with and without the truth layer.

Report to professor: “First numbers — here is the multi-hop accuracy cliff, and the lift our truth layer provides, measured on our own benchmark.”
M3 · Then

Expand under continuous QA

Grow the set toward balance (the thin templates) and add the auditing question family — every batch passing the same gate.

Report to professor: “The set grows safely — here is v1.x, the changelog, and the refreshed distribution.”

08Grounded in prior work

◆ Where the grading methods come from

FINAUDITING — we take its way of scoring retrieval by which facts were reached (Track R), its habit of separating computation failures by stage (Track C’s three results), and its subtotal/identity consistency checks (the auditing tier).

QuantEval — we take its rule that “does it run” is a separate score from “is it right,” and that a non-running answer is undefined rather than zero (the strategy-coding stretch).

FinTagging — it shows that grading on exact label match unfairly punishes correct-but-differently-named facts, which is why our grader credits a fact reached through an accepted alias rather than demanding one exact spelling.

⚠ Citation to correct in the earlier docs

Our existing PRD and bridge-design docs cite FinTagging as “17% semantic / 0% full-taxonomy” accuracy. On a close read that’s slightly off: FinTagging’s own result is 0% when the task is posed as a single step, with fine-grained tagging peaking below ~19% even in its easier two-step form; the “17%” figure was actually a different system’s number quoted in their related-work section. Recommend patching that line in the earlier docs separately — flagging rather than silently changing it.
